## 技術決策分析

### 決策 1：目標平台 ✅ PWA

#### 選項比較

| 方案 | 開發時間 | 跨平台 | 動畫效能 | 離線支援 | 分享功能 | 推播通知 |
|------|----------|--------|----------|----------|----------|----------|
| **PWA** | ⭐⭐⭐ 快 | ✅ 全平台 | ⭐⭐ 良好 | ✅ Service Worker | ✅ Web Share API | ⚠️ iOS 受限 |
| React Native | ⭐⭐ 中 | ✅ iOS/Android | ⭐⭐⭐ 優秀 | ✅ 原生支援 | ✅ 原生支援 | ✅ 完整支援 |
| Flutter | ⭐⭐ 中 | ✅ 全平台 | ⭐⭐⭐ 優秀 | ✅ 原生支援 | ✅ 原生支援 | ✅ 完整支援 |
| 原生開發 | ⭐ 慢 | ❌ 需雙平台 | ⭐⭐⭐ 最佳 | ✅ 原生支援 | ✅ 原生支援 | ✅ 完整支援 |

#### 決策理由

**選擇 PWA 的原因**：

1. **最快上市時間**
   - 單一代碼庫覆蓋所有平台（桌面、手機、平板）
   - 無需 App Store 審核流程
   - 可即時更新，無需用戶手動升級

2. **足夠的功能支援**
   - Web Animations API + CSS 可實現所需動畫效果
   - IndexedDB 支援大量本地儲存
   - Web Share API 支援社群分享
   - 可安裝到主畫面，類似原生 App 體驗

3. **低門檻驗證市場**
   - 用戶無需下載安裝，URL 即可使用
   - 快速迭代收集回饋
   - 若市場反應佳，可後續轉為原生 App

4. **成本效益**
   - 開發維護成本最低
   - 不需要 Apple Developer / Google Play 費用
   - 適合 MVP 階段

**接受的限制**：
- iOS 推播通知功能受限（iOS 16.4+ 已支援，但用戶需主動開啟）
- 部分硬體功能無法存取（此專案不需要）

**技術棧決定**：
- **框架**：React 18 + TypeScript
- **建置工具**：Vite
- **PWA 工具**：Vite PWA Plugin + Workbox

### 決策 2：動畫方案 ✅ Framer Motion + Lottie

#### 選項比較

| 方案 | 學習曲線 | React 整合 | 複雜動畫 | 效能 | 套件大小 |
|------|----------|------------|----------|------|----------|
| CSS Animations | ⭐⭐⭐ 低 | ⭐⭐ 手動 | ⭐ 困難 | ⭐⭐⭐ 最佳 | 0 KB |
| **Framer Motion** | ⭐⭐ 中 | ⭐⭐⭐ 原生 | ⭐⭐⭐ 優秀 | ⭐⭐ 良好 | ~50 KB |
| **Lottie** | ⭐⭐⭐ 低 | ⭐⭐ 良好 | ⭐⭐⭐ 最佳 | ⭐⭐ 良好 | ~40 KB |
| GSAP | ⭐ 高 | ⭐⭐ 手動 | ⭐⭐⭐ 專業 | ⭐⭐⭐ 優秀 | ~60 KB |

#### 決策理由

**選擇 Framer Motion + Lottie 組合**：

1. **Framer Motion 負責互動動畫**
   - 任務完成的打勾效果
   - 連線形成的畫線動畫
   - 格子點擊的縮放回饋
   - 連擊數字的彈跳效果
   - 手勢互動（長按、拖曳）

   ```typescript
   // 範例：任務完成動畫
   <motion.div
     animate={{ scale: [1, 1.2, 1] }}
     transition={{ duration: 0.3 }}
   >
     ✓
   </motion.div>
   ```

2. **Lottie 負責慶祝特效**
   - 連線完成的煙火效果
   - 全清的 confetti 動畫
   - 成就解鎖的徽章動畫
   - 可使用 LottieFiles 免費資源

3. **CSS 負責基礎過渡**
   - 顏色變化
   - 透明度淡入淡出
   - 簡單位移

**效能優化策略**：
- 使用 `will-change` 提示瀏覽器
- 動畫優先使用 `transform` 和 `opacity`
- Lottie 動畫設為 `lazyload`
- 複雜動畫使用 `requestAnimationFrame`

### 決策 3：儲存策略 ✅ 本地優先（IndexedDB）

#### 選項比較

| 方案 | 離線支援 | 跨裝置同步 | 開發複雜度 | 隱私保護 | 營運成本 |
|------|----------|------------|------------|----------|----------|
| **IndexedDB** | ✅ 完整 | ❌ 無 | ⭐⭐⭐ 低 | ✅ 本地 | $0 |
| Firebase | ⚠️ 需配置 | ✅ 即時 | ⭐⭐ 中 | ⚠️ 雲端 | 按用量 |
| Supabase | ⚠️ 需配置 | ✅ 即時 | ⭐⭐ 中 | ⚠️ 雲端 | 按用量 |
| 自建後端 | ⚠️ 需配置 | ✅ 可控 | ⭐ 高 | ✅ 自控 | 伺服器費 |

#### 決策理由

**選擇本地優先（IndexedDB）的原因**：

1. **MVP 階段最佳選擇**
   - 無需帳號系統，降低使用門檻
   - 零營運成本
   - 開發快速

2. **完整離線支援**
   - 通勤、飛行模式皆可使用
   - 無網路延遲，即時回饋

3. **隱私友善**
   - 用戶資料不離開裝置
   - 符合隱私優先趨勢
   - 無 GDPR 合規問題

4. **為未來同步預留架構**
   - 使用 Dexie.js 作為 IndexedDB 封裝
   - 設計資料層抽象介面
   - 未來可加入 Dexie Cloud 或自建同步

**技術實現**：
```typescript
// 使用 Dexie.js 封裝
import Dexie from 'dexie';

const db = new Dexie('BingoTodo');
db.version(1).stores({
  boards: '++id, date, status',
  tasks: '++id, boardId, name, category, position, completed',
  achievements: '++id, type, unlockedAt',
  stats: '++id, date, completionRate, lines, maxCombo'
});
```

**資料備份方案**：
- 提供匯出 JSON 功能
- 提供匯入還原功能
- 未來可選擇性同步到雲端

### 決策 4：差異化定位 ✅ 策略性 + 新鮮感

#### 競品痛點分析

| 競品 | 模式 | 痛點 |
|------|------|------|
| Habitica | RPG 養成 | 系統複雜、學習成本高 |
| Forest | 專注計時 | 僅限專注場景、無任務管理 |
| Todoist | 傳統清單 | 無遊戲性、積壓壓力 |
| Finch | 寵物養成 | 偏情緒照顧、非生產力 |

#### 核心差異化

**1. Bingo 連線的策略性**

- **任務配置思考**：用戶需思考哪些任務放角落（較難完成連線）、哪些放邊緣（多條連線經過）
- **風險與報酬**：困難任務放角落，完成時能同時完成對角線
- **策略深度**：不只是打勾，而是「玩」待辦事項

**2. 每日重置的新鮮感**

- **無積壓壓力**：傳統待辦清單會累積未完成項目造成焦慮
- **每天新開始**：新的 Bingo 板 = 新的機會
- **適度挑戰**：8 個任務是可完成的數量，不會過載

**3. 明確的完成感**

- **視覺化進度**：連線清楚顯示完成狀態
- **多重成就感**：每條連線都是一次小勝利
- **Full House 大滿貫**：全清的終極目標

#### 行銷定位語

> **「把待辦事項變成每日 Bingo 挑戰」**
>
> 不再是無盡的清單，而是每天 8 個任務的策略遊戲。
> 完成連線，獲得成就，讓生產力變得有趣。

## 技術決策總結

| 項目 | 決策 | 理由 |
|------|------|------|
| **平台** | PWA (React + Vite) | 最快上市、低成本驗證市場 |
| **動畫** | Framer Motion + Lottie | 互動動畫 + 慶祝特效的最佳組合 |
| **儲存** | IndexedDB (Dexie.js) | 本地優先、零成本、隱私友善 |
| **定位** | 策略性 Bingo + 每日重置 | 差異化於傳統待辦清單 |
