# 研究計畫：Bingo 待辦事項

**功能分支**：`001-bingo-todo`
**建立日期**：2025-11-19
**狀態**：Phase 0 研究階段

## 研究目標

在進入實作規劃（Phase 1）之前，需要完成以下研究項目，以確定技術選型和架構決策。

---

## 研究項目清單

### R-001：目標平台決策

**問題**：此應用程式應該是 Web App、Mobile App（iOS/Android）還是跨平台？

**研究要點**：
- [ ] 主要使用情境分析（通勤時用手機？桌前用電腦？）
- [ ] 各平台開發成本比較
- [ ] 推播通知需求（提醒完成任務）
- [ ] 離線使用需求優先級
- [ ] 目標用戶的裝置使用習慣

**可能選項**：
1. **PWA（Progressive Web App）**：跨平台、可安裝、支援離線
2. **React Native / Flutter**：原生體驗、單一代碼庫
3. **原生 iOS + Android**：最佳效能、最高成本
4. **純 Web App**：最快開發、功能受限

**決策依據**：開發資源、上線時程、用戶體驗優先級

---

### R-002：前端框架選型

**問題**：根據平台決策，選擇合適的前端技術棧。

**研究要點**：
- [ ] 動畫效果支援度（連線動畫、慶祝特效）
- [ ] 手勢互動支援（拖曳、點擊回饋）
- [ ] 狀態管理複雜度
- [ ] 社群生態與套件豐富度
- [ ] 團隊熟悉度

**可能選項**：
| 平台 | 框架選項 |
|------|----------|
| Web/PWA | React、Vue 3、Svelte |
| 跨平台 | React Native、Flutter、Tauri |
| iOS 原生 | SwiftUI、UIKit |

**評估標準**：動畫效能、開發速度、維護成本

---

### R-003：動畫與視覺效果方案

**問題**：如何實現流暢的連線動畫和慶祝特效？

**研究要點**：
- [ ] 連線形成時的畫線動畫實現方式
- [ ] 格子完成時的打勾/變色過渡效果
- [ ] 全清時的慶祝動畫（confetti、煙火等）
- [ ] 連擊加成的視覺提示
- [ ] 效能考量（60fps 流暢度）

**可能選項**：
1. **CSS Animations + Transitions**：輕量、效能好
2. **Framer Motion（React）**：宣告式、功能豐富
3. **Lottie**：設計師友善、After Effects 匯出
4. **Canvas / WebGL**：高效能粒子效果
5. **GSAP**：專業級動畫控制

**評估標準**：視覺品質、開發複雜度、檔案大小

---

### R-004：音效解決方案

**問題**：如何實現跨平台的音效回饋？

**研究要點**：
- [ ] Web Audio API vs HTML5 Audio
- [ ] 行動裝置的音效限制（需用戶互動觸發）
- [ ] 音效檔案格式與大小優化
- [ ] 靜音/音量控制實現
- [ ] 多音效同時播放支援

**可能選項**：
1. **Howler.js**：跨瀏覽器、功能完整
2. **Tone.js**：程式化音效生成
3. **原生 Web Audio API**：輕量、需自行封裝
4. **平台原生 API**：最佳相容性

**評估標準**：瀏覽器支援度、延遲、檔案大小

---

### R-005：資料持久化策略

**問題**：如何儲存 Bingo 板狀態、歷史記錄和用戶設定？

**研究要點**：
- [ ] 本地優先 vs 雲端優先
- [ ] 離線支援需求
- [ ] 跨裝置同步需求
- [ ] 資料量估算（每日一板 × 365 天）
- [ ] 隱私考量（是否需要帳號系統）

**可能選項**：
| 方案 | 優點 | 缺點 |
|------|------|------|
| LocalStorage/IndexedDB | 簡單、離線 | 無同步、容量限制 |
| SQLite（本地） | 結構化、高效能 | 需要原生橋接 |
| Firebase/Supabase | 即時同步、免維護 | 需要帳號、網路依賴 |
| 自建後端 | 完全控制 | 開發維護成本高 |

**決策依據**：MVP 階段可先用本地儲存，後續再加同步

---

### R-006：分享圖片生成技術

**問題**：如何將 Bingo 板狀態生成可分享的圖片？

**研究要點**：
- [ ] DOM to Image 轉換方案
- [ ] 圖片品質與檔案大小平衡
- [ ] 自訂樣式（加浮水印、品牌元素）
- [ ] 各社群平台的圖片尺寸需求
- [ ] 行動裝置的分享 API 支援

**可能選項**：
1. **html2canvas**：DOM 截圖、廣泛使用
2. **dom-to-image**：SVG 為基礎、品質較好
3. **Canvas API 自繪**：完全控制、較複雜
4. **Server-side 生成**：品質穩定、需要後端

**評估標準**：生成速度、圖片品質、跨平台支援

---

### R-007：成就系統設計模式

**問題**：如何設計可擴展的成就解鎖機制？

**研究要點**：
- [ ] 成就條件的定義方式（JSON Schema? 程式碼？）
- [ ] 事件驅動 vs 輪詢檢查
- [ ] 成就進度追蹤（如：完成 10/100 個任務）
- [ ] 新成就上線時的向下相容
- [ ] 成就通知的觸發時機

**設計考量**：
- 成就條件類型：計數型、連續型、組合型
- 解鎖檢查時機：任務完成時、應用啟動時
- 資料結構：成就定義與用戶進度分離

---

### R-008：競品分析

**問題**：市場上類似的遊戲化待辦工具有哪些？我們的差異化在哪裡？

**研究目標**：
- [ ] Habitica - 遊戲化習慣追蹤
- [ ] Forest - 專注時間遊戲化
- [ ] Todoist - 傳統待辦 + 積分系統
- [ ] Finch - 寵物養成 + 自我照顧
- [ ] 其他 Bingo 類應用

**分析要點**：
- 核心遊戲機制
- 獎勵系統設計
- 社交功能
- 付費模式
- 用戶評價與痛點

**差異化方向**：Bingo 連線的策略性、每日重置的新鮮感
